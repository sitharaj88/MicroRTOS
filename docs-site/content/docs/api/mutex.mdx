title: Mutex
description: Recursive mutexes with priority inheritance to prevent unbounded priority inversion.
---

Mutexes are the most common synchronization primitive. MicroRTOS mutexes
are **recursive** (a task can lock its own mutex N times) and implement
**priority inheritance** to prevent unbounded priority inversion.

Enabled by `MR_USE_MUTEXES=1` (default).

```c
#include "micrortos.h"
```

---

## Why priority inheritance?

Without PI, this classic bug bites: low-priority task L holds a mutex,
high-priority task H wants it and blocks, then a medium-priority task M
preempts L (and keeps running indefinitely because H is blocked). H is
effectively waiting on M — unbounded inversion.

With PI, when H blocks on L's mutex, L is **temporarily boosted to H's
priority**. M can no longer preempt L. When L releases, L returns to its
base priority and H runs. The kernel does this for you.

A task can lock its own mutex N times. Each lock must be matched by an
`mr_mutex_unlock`. The mutex stays held until the recursion count
returns to zero.

## `mr_mutex_unlock`

Releases one level of recursion. If the count reaches 0, wakes the
highest-priority waiter (if any).

<Signature
  name="mr_mutex_unlock"
  signature={`mr_status_t mr_mutex_unlock(mr_mutex_t *mutex);`}
  badges={[
    { label: 'May preempt', variant: 'warning' },
  ]}
/>

<ApiSection title="Returns">

<Returns type="mr_status_t" description="MR_OK on success." />

<ErrorTable
  className="mt-3"
  rows={[
    { code: 'MR_ERR_STATE', description: 'Called by a task that does not hold the mutex.' },
    { code: 'MR_ERR_PARAM', description: 'mutex is NULL.' },
  ]}
/>

</ApiSection>

<Callout type="warn">
Releasing a mutex you don't own is a serious bug. The kernel returns an
error rather than corrupting state, but always pair lock with unlock
explicitly.
</Callout>

## Complete example

```c
static mr_mutex_t spi_lock;

void init(void) {
    mr_mutex_init(&spi_lock);
}

uint16_t read_sensor(uint8_t addr) {
    if (mr_mutex_lock(&spi_lock, MR_MS_TO_TICKS(100)) != MR_OK) {
        return 0xFFFF;     /* peripheral busy too long — caller decides */
    }
    spi_select(addr);
    uint16_t val = spi_xfer();
    spi_deselect();
    mr_mutex_unlock(&spi_lock);
    return val;
}
```

## Anti-patterns

<Callout type="warn">

**Don't lock a mutex from an ISR.** ISRs can't block. Use a semaphore
or task notification with `_from_isr` instead.

**Don't hold a mutex across `mr_task_delay`.** Hold for as little time
as possible. Holding across a delay invites priority inversions.

**Don't use a mutex as a signal.** Mutexes are for mutual exclusion —
one owner, one path. For "wake me when X happens," use a
[semaphore](/docs/api/semaphore) or a [task notification](/docs/api/notifications).

</Callout>
